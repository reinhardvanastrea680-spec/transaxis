Application request and data flow

Solid arrows are the main request paths; the dashed line marks a privileged server-only path.

Typical path: route request → session refresh → server-rendered page → browser interaction → server action → authenticated database write. The main pages call auth.getUser() and check organization membership; Postgres RLS is the tenant boundary.

Core domain and operational flows

Entities and behaviors confirmed in pages, server actions, and SQL.

01 Tenant + team

organizations → profiles
profiles = org_id + role

First sign-in creates or joins an organization. Every business record is intended to be scoped to that organization; owners/admins manage staff and join codes.

onboarding/actions.ts · staff/actions.ts · schema.sql

02 Inventory ledger

products + stock_movements
→ product_stock view

Stock is derived from movements: inbound and adjustments add, outbound movements subtract. Stocktake variances become adjustment events rather than overwriting a balance.

inventory/actions.ts · stocktaking-client.tsx · schema.sql

03 Dispatch lifecycle

dispatches → dispatch_items
→ stock “out” movement

Creation checks available stock, records line items, deducts stock through a trusted server-side write, then tracks assignment, status, proof-of-delivery URL, and audit events.

dispatch/actions.ts · dispatch/page.tsx

04 Reports + accountability

audit_logs · CSV exports
inventory / movements / dispatches

Staff views expose role and audit history to permitted roles. Reports query current data and create CSV files in the browser; recent movement and dispatch exports are capped at 500 rows.

staff/page.tsx · reports/page.tsx · reports-client.tsx

Security boundaries and implementation notes

What the source actually shows.

Access model

  • src/lib/permissions.ts defines the application capability matrix; server actions re-check roles before writes.
  • SQL enables RLS and scopes data using current_org_id(); migration 003_rbac.sql adds role-aware policies and limits drivers to assigned dispatches.
  • Some trusted server actions use SUPABASE_SERVICE_ROLE_KEY for organization setup, staff administration, or dispatch stock side effects. The browser client uses the public anon key.

Scope / caveats

  • Proof of delivery is represented by a URL field on a dispatch; no upload/storage pipeline appeared in the inspected flow.
  • The landing-page dashboard preview uses sample values; the authenticated /dashboard fetches live Supabase data.
  • The package manifest defines dev, build, start, and lint; it has no test script.
Security reminder: keep the service-role key only in server environment variables. RLS remains important even when the UI hides actions, because client-side permission checks alone are not a security boundary.
